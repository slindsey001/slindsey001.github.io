Documentation dependency resolver

A static analysis tool that answers one question: which driver builds use this shared documentation file? Built at the 2026 CData hackathon.

Role
Technical writer and tool designer
Tools
Python, HTML, JavaScript
Scope
1,321 shared files across 307 drivers

Problem

CData documentation is assembled from shared content reused across more than 300 database drivers. Shared files reach a build through layers of includes, entities, bundles, chapters, and conditional rules, so a simple question had no simple answer: if I change this file, which drivers are affected?

Answering it meant repository-wide searches and manual investigation. The goal was to make that impact visible before anyone made the change.

How it works

The build system already knows what goes into a given driver. The resolver models that assembly process, then inverts it.

  1. Trace references through bundles, chapter includes, shared maps, and inline entities, transitively.
  2. Evaluate conditions so edition- and build-specific content only counts where it's actually included.
  3. Invert the graph into a lookup from any shared file to the drivers that consume it, recording how each one was reached.

It reads generated build indexes rather than guessing from file-name conventions, so results stay explainable.

Command line

Pass the path to a shared file and get back its consumers, grouped by how each was reached.

$ python doc-deps.py AzureProps/AzureAccessKey.prp
File:   ProviderBase/help/source/AzureProps/AzureAccessKey.prp
Entity: &AZUREPROPSpAzureAccessKey;
Via:    mixed

Direct body reference (3):
  ProviderDatabricks
  SyncADLS
  SyncAzureBlobDestination

Via shared .map, marked-section gated (10):
  ProviderAccess
  ProviderAvro
  ProviderCSV
  ProviderExcel
  ProviderJSON
  ProviderParquet
  ProviderREST
  ProviderSASDataSets
  ProviderSASXpt
  ProviderXML

Web interface

A searchable version for writers who'd rather not use the terminal, with each result labeled by how it's reached.

Validation

Conditional content was the hardest part. Early versions treated some edition-specific conditions too broadly and missed dependencies, so I compared resolver output against ground-truth repository searches to find and fix the gaps.

Some content is generated by the build itself and can't be traced through ordinary references. The tool flags those cases as unresolved or build-generated instead of overstating certainty.

Outcome

A question that took a repository-wide investigation now takes seconds. Writers use it for impact analysis before a change, for finding dependencies, and for spotting shared content that may be orphaned.
