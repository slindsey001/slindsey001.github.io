AI-assisted documentation review agent

A Claude-based reviewer that checks only the files changed in the current Git diff and returns structured, actionable findings. The writer stays in control of every change.

Role
Technical writer and agent designer
Tools
Claude, Git, Markdown
Outcome
Adopted across the CData docs team

Problem

Reviewing a docs change means more than checking grammar. Writers also verify implementation details, authentication, prerequisites, configuration, and API behavior against conventions. Most of those checks are important and repetitive. I wanted to see whether an AI reviewer could take on the repeatable ones without taking over the writer's judgment.

Approach

Instead of reviewing a whole docs set, the agent works from the changes already in Git.

  1. Scope the review to modified files in the current diff.
  2. Structure the findings by severity and docs area so the important ones surface first.
  3. Keep a human in the loop: the writer approves every change before it lands.

What it checks

Onboarding
Prerequisites, setup steps, missing context
Authentication
Setup, requirements, inconsistencies
API references
Outdated references, schema changes, accuracy
Configuration
Settings, properties, dependencies, unclear steps

Prompt design

Most iteration went into controlling scope. The goal was not more feedback, but feedback a writer could act on quickly.

Review the modified documentation files for outdated API references, missing prerequisites, authentication inconsistencies, schema drift, and unclear steps. Focus only on files changed in the current Git diff and prioritize actionable findings.

Example output

Outdated endpoint - Calls /v1/accounts. + Calls GET /v2/accounts. /v1 was deprecated in build 9123; the docs lagged.
Hardcoded secret in sample - Password=MyP@ssw0rd! + Password=<your-password> Copy-paste samples were leaking placeholder credentials into configs.
Schema drift - CreatedDate returned as string. + CreatedDate returned as datetime. Type changed in build 9088; ADO.NET users got cast errors.

What I learned

More feedback isn't better feedback. Early versions were verbose and repetitive, so most iteration focused on clarity, consistency, and prioritization. The output had to support the writer's judgment, not add another layer of work.
